# Smart Appointment Platform — Delivery Outcomes

Items remain open until implemented evidence supports completion.

## Authentication, accounts and access
- [x] Users can register, log in and log out; passwords are securely hashed; authentication uses JWTs and persistent sessions; protected routes require authentication; users can view and update permitted profile details, including their name, and change passwords securely; validation errors are displayed. Users cannot register themselves as administrators.
- [x] The application has exactly the requested User and Administrator roles, separates their layouts and routes, applies role-based authorization on the server and redirects authenticated users to the correct role experience. Administrator routes/APIs reject normal users. Passwords and password hashes are never exposed.

## User dashboard and booking workflow
- [x] The user dashboard displays a welcome message, total appointments, upcoming appointments, completed appointments, cancelled appointments, the next scheduled appointment, and recent booking activity.
- [x] Users can view available appointment dates, select a date using a calendar, view available time slots, select an available slot, review booking information, confirm the appointment, receive a unique booking reference, and receive success/error notifications. Only genuinely available slots are displayed as bookable.
- [x] Users can view appointment history in separate Upcoming, Completed and Cancelled categories. Each appointment shows its booking reference, date, start time, end time, booking status and booking details. Users can view appointment details and cancel eligible upcoming appointments. After cancellation, a slot becomes available again if it is still within the permitted booking period.

## Administrator dashboard and management
- [x] A separate administrator dashboard displays total registered users, total appointment slots, available slots, booked slots, total bookings, cancelled bookings and completed appointments; includes booking statistics, daily and weekly appointment charts, recent booking activity and useful dashboard summaries; and uses Recharts for visualizations.
- [x] Administrators can create slots, select appointment dates, define start/end times, edit slots, delete eligible slots, mark slots unavailable, and view available and booked slots. The system prevents duplicate/overlapping slots (including concurrent create/edit requests serialized on a unique UTC-day lock) and prevents slot date/time edits or deletion when booking history references that appointment; availability may still be changed when no active booking exists.
- [x] Administrators can view all bookings; search by booking reference; filter by date and booking status; view associated user details; mark appointments completed or no-show; and review cancellation history.
- [x] Administrators can view/search registered users, view user booking histories and safely activate/deactivate accounts if implemented. Passwords/password hashes are never exposed.

## Persistence and booking integrity
- [x] MongoDB/Mongoose data entities include Users (name, unique email, hashed password, role user/admin, isActive, createdAt, updatedAt), Slots (date, startTime, endTime, status available/booked/unavailable, createdBy, createdAt, updatedAt), and Bookings (userId, slotId, unique bookingReference, status confirmed/cancelled/completed/no-show, bookedAt, cancelledAt, createdAt, updatedAt), with ObjectId references and suitable indexes. The infrastructure `SlotScheduleLock` collection uniquely indexes each UTC day to serialize administrator schedule writes.
- [x] A slot never has more than one active booking. Users can only book available slots. The backend verifies slot availability and validates booking dates/times; the frontend is not trusted for availability. Two users cannot successfully book the same slot simultaneously. Booking uses atomic conditional updates or MongoDB transactions where supported; a failed booking creation safely releases a claimed slot; cancellation updates booking status and releases the slot consistently; duplicate booking requests are prevented.

## REST API and security
- [x] Express REST APIs include POST `/api/v1/auth/register`, `/login`, `/logout`; GET `/api/v1/auth/me`; GET `/api/v1/slots` and `/api/v1/slots/:id`; POST `/api/v1/bookings`; GET `/api/v1/bookings/my` and `/api/v1/bookings/:id`; PATCH `/api/v1/bookings/:id/cancel`; POST `/api/v1/admin/slots`; PUT/DELETE `/api/v1/admin/slots/:id`; GET `/api/v1/admin/bookings`; PATCH `/api/v1/admin/bookings/:id/status`; and GET `/api/v1/admin/dashboard`, `/analytics` and `/users`.
- [x] Backend code has controllers, routes, middleware and services; centralized error handling; input validation; appropriate HTTP status codes; and consistent API response formats.
- [x] Security includes bcrypt password hashing, secure JWT authentication, HTTP-only cookies where practical, authentication middleware, role-based authorization, admin-only API protection, input validation, authentication-endpoint rate limiting, Helmet security headers, correct CORS configuration, environment variables, and safe errors. Never expose passwords, password hashes, JWT secrets, database credentials or private environment variables. `.env.example` contains placeholder values only and actual secrets are never committed.
